# v0.6.0 手机浏览器上传设计

## 目标与边界

v0.6.0 增加“手机浏览器扫码上传到 PC”。PC 主动创建一个短时会话并展示二维码；手机与 PC 位于同一受信任局域网时，扫码打开由邻渡本地服务提供的页面，选择普通文件后提交上传请求。PC 必须逐批确认，确认后文件才写入用户授权的接收目录。

第一版只支持手机到 PC 的单向普通文件传输，不支持 PC 向手机发送、文字、文件夹、后台同步、相册自动备份、账号、公网中继或云存储。一次最多 20 个文件，每个文件继续受 PC 设置中的单文件上限约束。

手机不是协议 v3 的可信桌面设备，不进入最近设备、自动发现、桌面连接或可信设备列表，也不占用桌面端单对单 WebSocket 连接。移动上传可以与已连接桌面设备共存，但落盘任务通过独立协调器严格串行，避免多个手机批次并行占用磁盘。

## 用户流程

1. 用户在 PC 的“传输”页点击“手机上传”，邻渡创建五分钟有效的移动会话并显示二维码与同网段访问地址。
2. 二维码 URL 的 fragment 携带 256 bit 随机会话密钥。浏览器 fragment 不随初始页面请求发送；移动页面读取后把它作为自定义认证 header 提交。该方式兼容局域网 HTTP 的非安全浏览器上下文，不依赖只在 HTTPS 下开放的 Web Crypto `subtle` 或 `randomUUID`。
3. 手机选择文件并提交名称、MIME、大小和随机批次 ID。PC 显示来源 IP、文件数量和总大小，但不把会话密钥或手机提供的路径写入界面、历史或日志。
4. PC 用户接受到默认接收目录、另选本次目录或拒绝。只有接受后，主进程才签发短时、绑定来源 IP/批次/文件/分块的上传授权。
5. 手机按文件顺序和固定分块顺序上传，页面展示进度；PC 使用既有重名安全发布语义，完成后写入文件历史。
6. 用户可以随时关闭会话。会话过期、来源变化、拒绝、取消、超时或应用退出都会撤销未使用授权并清理当前批次的临时内容。

## 浏览器与传输安全模型

移动页面由 PC 的局域网 HTTP 服务提供。由于局域网 IP 通常没有受信任证书，第一版不能声称传输链路具备 HTTPS 或协议 v3 桌面端的端到端加密安全等级。局域网内能够主动嗅探或篡改 HTTP 的攻击者仍可能干扰页面或读取文件内容；产品必须在二维码弹窗和手机页面明确提示只在受信任网络使用。

以下控制用于防止普通网页跨站调用、盲扫端口和未授权上传，但不替代 HTTPS：

- 每次会话使用 `randomBytes(32)` 生成不可预测密钥，默认五分钟过期，只保存在主进程内存和二维码 fragment；URL query、请求日志和 Referer 均不得包含密钥。
- 页面响应设置严格 CSP、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Cross-Origin-Resource-Policy: same-origin` 和禁止嵌入策略；页面不加载任何公网资源或第三方脚本。
- API 不启用 CORS，也不处理预检请求。请求必须携带 fragment 中的高熵会话密钥、自定义 header、时间戳和 nonce；主进程使用定时安全比较校验密钥，并校验显式 Origin、来源 IP、时间窗及 nonce 去重。跨站网页无法在没有 CORS 预检许可时携带自定义认证 header。
- 元数据只接受严格 JSON 和精确 `Content-Length`。文件名使用现有跨平台单路径段规则，数量、单文件大小、总大小、MIME、批次和标识符均在 shared schema 与主进程状态机再次校验。
- 上传使用精确 `Content-Length` 的 `application/octet-stream` 固定分块；授权绑定会话、来源 IP、批次 ID、文件 ID、块序号、偏移、长度和截止时间，并在首次尝试时消费。
- PC 审批前不接受文件 body。审批弹窗只显示净化后的文件名和大小；手机不能指定 PC 保存路径。
- 移动会话、待审批批次、nonce、授权和终态任务都有 TTL 与数量上限。HTTP 路由继续使用独立限流，不放宽桌面 `/v1/ws` 对浏览器 Origin 的拒绝规则。

## 本地页面与 API

移动页面使用独立的静态 HTML、CSS 和原生 TypeScript/JavaScript 构建产物，不复用 Electron renderer，也不拥有 Preload、Node 或 Electron 能力。生产包内的页面资源由主进程以固定映射提供，不接受任意文件路径。

计划路由如下：

- `GET /mobile/:sessionId`：返回固定上传页面；只验证公开 sessionId 是否存在，不创建上传授权。
- `POST /mobile/:sessionId/offers`：提交一个文件批次元数据并等待 PC 决定。
- `GET /mobile/:sessionId/offers/:batchId`：查询审批及传输状态。
- `PUT /mobile/:sessionId/batches/:batchId/files/:fileId/chunks/:chunkIndex`：上传一个已授权分块。
- `POST /mobile/:sessionId/batches/:batchId/cancel`：取消待审批或活动批次。

所有 JSON 返回稳定错误码，不返回堆栈、绝对路径、内部 token 或其他会话信息。轮询使用有界间隔和 `Cache-Control: no-store`，第一版不为浏览器开放 WebSocket。

## 主进程、IPC 与界面边界

新增 `MobileUploadCoordinator` 作为移动会话、审批、分块和任务状态的唯一事实来源。它复用现有接收目录授权、文件名安全规则、临时文件权限、磁盘空间预检、重名发布、历史与防休眠模块，但不复用桌面设备身份或 v3 会话密钥。

shared 新增严格的移动会话 DTO、offer DTO、任务 DTO、IPC contracts、HTTP schemas 和稳定错误码。Preload 只增加具名方法：创建/关闭会话、取得当前会话、响应 offer、取消任务，以及对应只读事件订阅。renderer 只能看到二维码内容、局域网候选 URL、有效期和净化后的任务投影；不能看到会话密钥的拆分材料、上传授权、接收路径或临时路径。

二维码在 renderer 内根据主进程返回的完整 fragment URL 生成。项目加入 `qrcode@1.5.4` 和仅开发期使用的 `@types/qrcode@1.5.6`：前者只把给定字符串转换为二维码 data URL，不访问网络、不读取文件，也不接触 Node/Electron API；后者提供严格 TypeScript 类型。`qrcode` 使用 MIT 许可证，生产构建增加约 30 KiB 未压缩 renderer 代码。

## 历史、诊断与隐私

每个成功或终态文件继续写入既有文件历史，方向为接收，对端显示为“手机浏览器”，并增加可选来源种类 `mobile-browser`，不持久化完整 user-agent、会话 ID、认证材料或手机文件路径。IP 按现有历史规则处理，诊断导出继续隐藏主机位。

日志只记录移动会话生命周期、来源 IP 的既有脱敏形式、批次数量、任务状态和稳定错误码，不记录二维码 URL、fragment 密钥、认证 header、文件名、文件内容或完整目标路径。

## 分阶段路线

0. 需求范围、威胁模型、HTTP/API、IPC、存储和测试设计；本阶段只修改文档。
1. shared schema、类型、错误码、IPC 契约和 `MobileUploadCoordinator` 的纯状态机；创建与关闭内存会话，不提供 HTTP 页面。
2. 打包内置移动页面、认证请求协议、offer API、PC 二次审批和二维码展示；本阶段允许选择文件但不上传 body。
3. 固定分块上传、来源与授权绑定、临时文件、完整性校验、重名发布、进度、取消、防休眠和历史整合。
4. 多文件串行、会话/任务恢复边界、失败提示、响应式移动 UI、限流与安全回归。
5. Windows/macOS PC 与 iOS Safari、Android Chrome 的真实局域网验收，版本更新和候选发布收口。

每个阶段独立运行 `pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm test` 和 `pnpm build`。不得在前一阶段完成前实现后一阶段功能；阶段 5 实机矩阵完成前不得宣称移动上传已正式跨平台可用。

## 当前实施状态

阶段 0–4 已完成设计、shared 契约、短时二维码会话、内置移动页面、自定义 header 请求认证、PC 审批、4 MiB 固定分块串行上传、受控临时文件、重名安全发布、进度、取消和历史整合。自动化覆盖会话过期、非法文件名、认证缺失、nonce 重放和真实本机 HTTP 上传发布；现有桌面协议回归保持通过。

移动批次同时投影到传输页时间线，按收到时间与文字、桌面文件任务共同排序；批次卡展示总进度、逐文件状态、取消和完成后定位。手机页面允许一次多选或分多次继续添加，最多 20 个去重文件，可逐个移除并查看逐文件/总进度；单批完成后清空已传列表并恢复选择和请求按钮，可在二维码会话有效期内继续发起下一批。过长文件名保持单行并以省略号截断，文件大小与固定宽度的移除操作不会挤压换行。PC 弹窗采用扫码与确认双栏布局，展示当前局域网地址、按秒刷新的剩余有效期、文件清单及批次状态。多文件严格串行，0 字节文件以“已安全发布”而不是字节计数作为完成依据。

阶段 5 的 Windows/macOS PC 与 iOS Safari/Android Chrome 真实设备矩阵尚未执行，因此当前功能仍应视为测试功能，版本号保持 v0.5.0，不宣称正式移动端跨平台验收完成。

## 验收重点

- 二维码只在会话有效期内工作，关闭或过期后所有页面/API 均失败关闭。
- 同一二维码转发给另一来源地址时不能接管已提交批次；PC 必须看到并批准每个新批次。
- 跨站表单、带错误 Origin、缺失/重放认证 nonce、篡改正文、超时签名和错误来源均被拒绝。
- 审批前 body、乱序块、重复块、错误长度、chunked、错误 MIME、超量文件和并行上传均被拒绝。
- 断网、手机锁屏导致超时、PC 取消、磁盘不足和应用退出后，不发布部分文件并清理严格归属的临时文件。
- 中文、空格、括号、重复文件名、零字节及接近设置上限的文件均按既有安全语义工作。
- 页面在 iOS Safari 和 Android Chrome 可选择相册/文件、保持合理进度展示，并明确提示前台保持页面开启。
