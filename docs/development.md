# 开发指南

## 初始化

```bash
pnpm install
```

## 启动开发环境

```bash
pnpm dev
```

Vite 启动渲染进程开发服务器，Electron 主进程和 Preload 由 `vite-plugin-electron` 构建并启动。

应用名称为「邻渡」。应用使用固定左侧菜单；传输页只滚动内部活动时间线，历史页只滚动表格内容，其他页面使用右侧内容区滚动。传输页默认使用紧凑的两行编辑器，用户可纵向拖拽调整编辑器高度；待发送附件和发送队列折叠显示，点击摘要可展开管理，从而优先保留聊天时间线空间。首页连接状态以中文徽标展示：未连接、正在连接、等待对方确认、已连接、正在断开或连接异常。右上角按钮可切换深浅色主题，选择会在本机 renderer 存储中保留。

## 检查

```bash
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test
pnpm build
```

项目使用 TypeScript strict 模式，并额外开启 `noUncheckedIndexedAccess` 和 `exactOptionalPropertyTypes`。代码风格由 ESLint 与 Prettier 管理。

协议输入使用 Zod 做运行时校验，静态类型优先由 schema 推导。纯 shared 单元测试使用 Vitest：

```bash
pnpm test
pnpm test:watch
```

## Windows 打包开发

阶段 12 使用 `electron-builder`。安装此依赖是为了生成 Windows x64 应用目录和 NSIS 安装包；`build/icon.ico` 是 Windows 打包图标，渲染进程复用其高质量源文件 `build/icon.svg`。

建议在 Windows x64 环境执行：

```bash
pnpm package:win:dir
pnpm package:win
```

`package:win:dir` 先生成 `release/win-unpacked`，适合验证应用启动、资源路径和服务监听；`package:win` 生成正式的安装向导。两条命令都会先执行生产构建。当前配置可以在项目的 macOS 开发机生成 NSIS 包，但跨平台产物不能代替 Windows 实机的安装、卸载和防火墙验收；若构建机提示缺少兼容工具链，应改在 Windows x64 环境构建。

生产渲染资源使用相对 URL，以保证 `BrowserWindow.loadFile` 加载 `dist/index.html` 时能找到 JS、CSS 和 Logo。打包输出位于 `release/`，不得提交到 Git。

## macOS 打包开发

阶段 13 继续使用 electron-builder，不增加第三方依赖。`build/icon.icns` 是从品牌 SVG 生成并通过 `iconutil` 反向解析验证的多分辨率 macOS 图标。

```bash
pnpm package:mac:dir
pnpm package:mac:arm64
pnpm package:mac:x64
pnpm package:mac
```

- `package:mac:dir`：生成当前 CPU 架构的未压缩 `.app`，用于本机冒烟测试；
- `package:mac:arm64`：生成 Apple Silicon DMG；
- `package:mac:x64`：生成 Intel DMG；
- `package:mac`：依次生成两个架构的 DMG。

当前测试包显式禁用代码签名、notarization 和 Hardened Runtime，只允许开发验收，不适合公开分发。应用的最低系统版本为 macOS 12，Bundle ID 固定为 `com.lindu.transfer`。第一版不使用 Bonjour，因此 Info.plist 只声明本地网络用途，不声明 `NSBonjourServices`。

## IPC 开发约束

- 新 handler 必须使用 `registerIpcHandler`，不得直接分散调用 `ipcMain.handle`。
- channel、请求类型及 Zod schema 必须先加入 `src/shared/ipc`。
- Preload 只能增加具名方法，禁止暴露通用 IPC 方法。
- renderer 不得导入 Electron、Node.js 或主进程模块。

## 本地服务检查

开发模式启动后，首页会展示当前非 internal IPv4、实际服务端口和服务状态。可在本机验证健康检查：

```bash
curl http://127.0.0.1:53317/health
```

预期返回 HTTP 200 和协议版本。若端口被其他程序占用，首页应展示 `PORT_IN_USE` 对应的中文错误；本阶段不会自动选择随机端口。

## 双设备连接检查

在两台同局域网设备运行应用，在主动方输入另一台首页显示的 IPv4 和端口 53317。接收方必须出现审批弹窗；允许后双方显示对方设备信息，拒绝后双方回到未连接。继续检查主动断开、应用退出和错误端口。

macOS 或 Windows 防火墙提示应只允许受信任的专用网络。阶段 6 不发送文字或文件。

## 双设备文字检查

完成上述连接后进入“传输”页面：

1. Windows 向 macOS 发送普通文字，确认对端立即显示并可一键复制；
2. macOS 向 Windows 反向发送普通文字；
3. 双向发送完整 HTTP/HTTPS 链接，确认显示“链接”标记；
4. 点击“打开链接”，确认只有用户操作后才交给默认浏览器；
5. 使用“读取剪贴板”填入编辑框，再发送；
6. 断开连接，确认发送按钮禁用；输入超过 64 KiB 时同样不能发送；
7. 在同一次应用运行期间切换页面，确认最近文字仍可显示。

文字和文件历史会写入本地 store；文字仅保存最多 500 个字符的预览。重启应用后可以在传输页恢复最近文字摘要，也可以在历史页面筛选或清空记录。

## 双设备文件检查

建立连接后在发送方进入“传输”，点击“添加文件”或把文件拖入统一编辑器。选择结果先进入待发送区，不会立即通知对端；可以逐个移除、清空，或同时输入一段文字后点击“发送”。选择授权保留 10 分钟。接收方会自动进入传输页，并在对应时间线卡片中选择接收到系统 Downloads、通过系统选择器更改本次目录，或拒绝文件。

分别从 Windows 和 macOS 双向验证普通文件、中文文件名、空格、括号、0 字节、1 MB、100 MB、接近设置上限的大文件和同名文件。观察双方文件名、MIME、大小、进度、速度及最终状态；同名目标不能被覆盖。传输过程中拔网线或退出接收端，确认最终文件不出现，随机 `.part` 文件被清理。

继续选择 2–20 个文件并验证严格串行上传、总进度与逐文件状态。分别测试系统多选和拖拽；拖入文件夹或超过 20 个文件应被拒绝。测试取消整个任务、取消当前文件、取消待传文件，以及失败/拒绝/取消后的重试；确认重试创建新任务，已成功文件不回滚且同名目标不覆盖。

统一编辑器还需检查：只发送文字、只发送文件、文字与文件一起发送、移除单个待发送文件、清空待发送区，以及 Enter 快捷发送和 Shift+Enter 换行。使用中文等输入法确认候选文字时不得误发送。文字与文件一起发送时会依次形成两条独立记录；文字发送失败时不会继续发起文件 offer，避免在连接已经异常时制造第二个失败任务。若连接在正式发送前断开，待发送文件会被清空并要求重新选择，避免重连到其他设备后误发。

## 本地设置与历史检查

设置页面可修改设备名、服务端口、最大单文件大小和历史上限，默认接收目录必须通过系统目录选择器授权。修改端口后确认服务立即以新端口运行；占用目标端口时应显示错误并继续使用旧端口。重启应用后确认设备 ID、设置和历史均保持不变。

成功连接设备后，断开并重启应用，首页应使用最近设备预填 IP 和端口，但不能自动连接。完成双向文字、文件、拒绝和取消操作后，在历史页面按方向、类型和状态筛选，检查分页与清空确认框。将历史上限调低后应立即删除最旧记录。

本地文件位于 Electron 标准 `userData` 目录，不应手工编辑。测试损坏配置时应先备份整个测试用户数据目录；应用会把无法通过校验的 store 改名为 `.invalid-时间戳` 并恢复默认值。

历史页搜索框会匹配文字摘要、文件名、设备名和 IP，并与方向、类型、状态筛选共同生效。搜索和筛选必须在分页前完成；“全部方向”“全部类型”“全部状态”应显示中文选项，不得显示默认 `Select`。状态图标应在浅色、深色和各缩放比例下保持居中。

## 异常与安全检查

阶段 11 后应额外执行：

1. 尝试拖拽文件夹、文件符号链接和相对路径，确认无法签发发送 token；
2. 尝试选择磁盘根、系统目录、应用数据目录或安装目录作为接收目录，确认被拒绝；
3. 将已选择文件替换、修改或改为符号链接后再接受，确认任务以 `FILE_NOT_FOUND` 失败；
4. 上传中断网或暂停数据超过 30 秒，确认双方超时且 `.part` 被清理；
5. 重复提交同一上传 token，确认不会覆盖或生成第二份文件；
6. 构造错误 Content-Length、chunked 上传、错误 MIME、过期 token、乱序文件和超量 body，确认请求失败；
7. 创建严格匹配命名且超过 24 小时的测试 `.part` 文件，重启后确认仅该文件被清理；
8. 检查 Electron 标准日志目录，确认包含应用、服务、连接和传输状态，但不包含文字正文、剪贴板、token、文件内容或完整文件路径。

限流测试应只在隔离环境执行，避免把正常设备暂时限制。磁盘不足、Windows 文件锁和真实断网仍需在双平台手动验证。

## 阶段

项目严格按需求与架构、初始化、共享协议、安全基础、本地服务、设备连接、文字、文件、多文件、存储、安全完善、双平台打包和验收的顺序推进。

## 1.1 自动发现与传输可靠性

本阶段不新增第三方依赖，UDP 使用 Node `dgram`，传输防挂起和文件定位使用 Electron 内置 API。开发环境启动两份独立应用实例时，它们必须使用不同 userData 和服务端口，但共享 UDP 发现端口；`reuseAddr` 允许多个实例接收组播。

自动发现依赖网络允许 IPv4 组播。企业网络、访客 Wi-Fi、AP 隔离、VPN 和防火墙可能屏蔽 UDP 53318，此时继续使用首页手动 IP/端口。发现设备点击连接后仍需在对端批准。传输中关闭应用会出现确认；选择退出会走既有取消和 `.part` 清理流程。

## 1.2 文件夹传输与批量任务

1.2 严格按以下阶段实施，每个阶段单独执行质量门禁、提交和推送：

1. 文件夹需求、manifest、路径规则、协议、IPC、安全发布和错误码设计；
2. 主进程安全递归扫描、系统文件夹选择、拖拽入口和短期授权；
3. manifest 分片、folder offer、接收确认、协议版本 2 和基础 UI；
4. 逐文件 HTTP 流、空目录创建、任务/文件进度、速度、取消和超时；
5. 最终目录安全发布、同名处理、异常清理、重试和历史；
6. 文件、文件夹和文字的多任务串行队列；
7. 后台系统通知、传输完成摘要和失败项展示；
8. 路径/manifest/重放/中断安全完善与 Windows/macOS 双平台验收。

阶段 1 只修改文档，不提前新增协议代码或文件夹业务。完整决策见 [文件夹传输设计](folder-transfer.md)。

阶段 2 不新增依赖，使用 Node `fs/promises` 完成有界递归扫描。系统选择器返回一个文件夹摘要；拖拽入口支持普通文件和文件夹混合，但包含文件夹时最多 10 个顶层项目，纯文件拖拽继续允许原有 20 个。扫描授权有效 10 分钟，本阶段只支持在待发送区预览和移除文件夹，不发送网络 offer。

阶段 3 不新增依赖，协议升级为 v2。`FolderTransferCoordinator` 负责 folder offer、manifest 有界分片与重组、接收审批和任务投影；renderer 每次只允许一个待发送文件夹，并继续通过统一 offer 事件响应文件或文件夹。接受后的 uploadKey 只保存在主进程，本阶段不注册文件夹 HTTP 上传路由，因此任务停留在“已接受”。阶段 4 才实现逐文件流和空目录落盘。

阶段 4 不新增依赖，复用 Node `crypto`、`http`、`fs` 和 stream。任务级 uploadKey 通过 HMAC-SHA-256 派生逐文件 bearer token，HTTP 路由按 manifest 顺序逐个消费。接收内容写入授权目录内的独占隐藏 staging 树；进度和速度通过既有任务事件展示，文件夹取消只支持整个任务。全部内容完成后状态为 `publishing`，阶段 5 前不会显示为最终完成，也不会写入历史。

阶段 5 不新增依赖。`folder-publish` 负责独占最终目录、同名递增、ownership marker、顶层内容移动和严格残留清理；协调器只在发布成功后发送 folder-scope complete、保存最终路径并记录历史。文件夹重试复用已授权源快照，但生成全新的任务/文件 ID 和网络授权，上传前仍会再次核对源文件身份。

阶段 6 不新增依赖。`TransferQueueCoordinator` 是出站组合发送的队列事实来源：一次点击按文字、文件批次、文件夹顺序入队，入队时原子消费全部 selection token 并持有主进程授权快照。队列等待文件或文件夹任务进入 completed、failed、cancelled 或 rejected 后再启动下一项；活动接收任务占用协调器时只等待。断线删除尚未启动的项，队列项绑定入队时的 peer deviceId，不能在重连后发给另一设备。renderer 只接收队列摘要和位置，可移除等待/失败项，不能看到路径或授权。

阶段 7 不新增依赖，使用 Electron 内置 `Notification`。仅在主窗口未聚焦、已最小化或没有窗口时通知收到文字/链接、文件/文件夹 offer 以及文件/文件夹完成或失败；前台事件仍被记录为已观察，之后切到后台不会补发旧通知。通知只包含对端设备名、内容类型、项目数量和结果，不包含正文、文件名、文件夹名、路径或 token；点击通知会恢复、重建并聚焦主窗口。终态通知按 transferId/status 有界去重。

传输任务卡在终态汇总成功、失败、取消和拒绝数量。未完成项目直接展示本地化错误原因，默认最多显示 20 项，剩余数量提示用户展开原有文件明细；这只是 renderer 投影，不改变任务状态机、历史或重试语义。

阶段 8 不新增依赖。扫描器在 realpath 前后复核设备号、inode 和文件类型，降低扫描期间被替换为符号链接或其他条目的风险；生成 manifest 前对完整可移植相对路径重新排序。Windows 保留名校验额外覆盖 `COM¹/²/³` 与 `LPT¹/²/³`。

接收端对每个 manifest 分片执行 96 KiB 上限、空分片规则、累计文件/空目录数量、累计大小和 2 MiB 部分 manifest 限制，完整后再强制路径排序、ID 唯一、父子终端冲突和摘要一致。终态 folder transferId 保留 24 小时且最多 2,000 个，用于拒绝使用新 messageId 重放旧 offer；协调器只保留最多 100 个终态任务，避免长期运行无界增长。真实 HTTP 中断测试确认连接关闭会使双方失败并清理 staging。

## v0.3.0 数据管理与故障诊断

v0.3.0 按以下阶段实施，完整设计见 [v0.3.0 设计](v0.3.0.md)：

0. 需求边界、IPC 草案、存储迁移和诊断脱敏规则；
1. shared 契约、设置/最近设备迁移及存储测试；
2. 历史统计、单条/批量/条件清理和页面交互；
3. 最近设备备注、删除、在线状态与一键连接；
4. 诊断中心、目录操作、报告导出和日志生命周期；
5. 错误处理建议、恢复入口和任务卡体验；
6. 数据迁移、双平台验收和 v0.3.0 发布。

阶段 0 只修改文档。v0.3.0 不新增网络消息，Preload 仍只暴露具名 IPC；任何清理、目录打开或报告导出都由主进程操作固定路径或系统对话框，renderer 不获得任意文件能力。

阶段 1 不新增依赖。设置和最近设备 store 使用显式 schemaVersion 2，启动时先识别并迁移合法 v1 数据，再交给 electron-store；迁移写入使用同目录临时文件和替换流程，不能把合法旧数据误判为损坏。shared 已定义保留策略、历史清理、最近设备 alias 和诊断 DTO，但新 IPC channel 等对应主进程 handler 与 Preload API 同阶段出现，保持白名单可调用面完整。

阶段 2 不新增依赖。历史页显示总数、筛选匹配数和 `history.json` 大小，支持单条、批量、当前筛选、失败状态和指定时间以前的摘要清理。条件清理必须先由主进程返回命中数量并经用户确认；所有操作只改写历史摘要，绝不删除接收目录内的文件。历史保留天数默认关闭，启用后在启动及保存设置时清理过期摘要。

阶段 3 不新增依赖。首页最近设备按 deviceId 与自动发现结果合并在线状态；在线设备连接时优先使用发现到的当前地址，离线设备使用上次成功地址。设备备注、单项删除和清空均通过具名 IPC 操作主进程 store，备注不参与握手、广播、日志或连接审批，最近设备也不代表可信设备。

阶段 4 不新增依赖。诊断页从主进程读取应用、服务、发现、连接、活动任务、历史和日志摘要；固定数据/日志目录只能由无参数 IPC 打开。JSON 报告通过系统保存对话框和同目录临时文件导出，完整 IP 会隐藏主机位，且不包含正文、文件名、设备名、备注、令牌、内部 ID、完整路径或日志正文。日志统计和清理只处理日志目录内已知名称的普通文件，跳过符号链接、目录和当前活动日志；设置页可配置 1–3650 天的旧日志保留期。

阶段 5 不新增依赖，也不改变协议错误码。每个稳定错误码都有穷尽的本地中文处理建议和恢复动作分类；连接异常状态允许直接重新连接，传输卡按错误提供首页或设置入口。文件/文件夹重试前明确确认会创建新任务并从头传输，缺失或变化的源内容提示重新选择，不宣称断点续传。

阶段 6 将应用版本更新为 `0.3.0`，执行全部自动化、生产构建和当前平台目录包结构检查，并冻结候选发布清单。跨平台构建不替代实机：Windows 安装/卸载/防火墙/文件锁、Intel Mac 启动，以及 Windows/macOS 双机矩阵在真实设备签字前均保持待验收。
