# v0.5.0 正式分发与安全更新设计

## 目标与边界

v0.5.0 把邻渡从未签名候选包推进到可验证来源的正式安装包，并提供由用户控制的安全更新。Windows x64 安装包使用 Authenticode 签名，macOS arm64/x64 应用启用 Hardened Runtime、Developer ID 签名和 notarization；稳定版本通过 GitHub Releases 发布，应用可检查、下载并在安全时机安装新版本。

本版本不改变局域网传输协议 v3，不新增公网中继、账号、云历史或遥测。更新功能访问公网只用于读取发布元数据和下载安装包；局域网文字、文件、设备身份、可信设备、历史和恢复任务都不会上传。离线环境中的连接与传输能力必须保持完整。

v0.4.0 的真实 Windows/macOS 安全、安装和双机恢复签字仍是正式发布 v0.5.0 的前置门禁。规划和不依赖正式凭据的开发可以先行，但不得用 v0.5.0 掩盖或跳过 v0.4.0 未完成的实机验收。

## 锁定决策

- 正式更新源使用项目 GitHub Releases；第一版只提供 `stable` 渠道，不实现灰度、测试渠道或私有更新服务器；
- 更新检查默认启用，应用启动后延迟执行且最多每 24 小时自动检查一次；用户可以关闭自动检查并随时手动检查；
- 自动检查失败不得阻塞启动、局域网连接或传输，也不得反复弹窗；手动检查失败才展示明确错误；
- 应用可以在后台下载更新，但不会静默退出或重启；安装必须由用户明确触发；
- 存在配对审批、活动传输、队列发送、校验、发布或自动重连时禁止安装，待任务进入安全状态后再提示；可恢复任务本身不阻止安装，但更新前必须确认其加密记录已持久化；
- 更新状态、下载和安装只由主进程管理。Preload 只暴露具名 IPC，renderer 不接触发布 URL、任意文件路径、安装器路径、签名材料或通用网络能力；
- 更新只接受 HTTPS 固定来源。release 元数据、版本、平台、架构和产物名称必须严格校验，不能接受 renderer 或网络消息提供的任意 URL；
- macOS 产物必须通过 Developer ID 签名、Hardened Runtime、notarization 和 stapling；Windows 安装包与可执行文件必须通过受信任代码签名证书签名；
- 证书、私钥、密码、notarization 凭据和发布令牌只进入本机安全凭据存储或 CI secret，不写入仓库、构建日志、诊断报告或发布元数据；
- 同一版本的所有产物必须来自同一 Git 提交，发布记录保存提交、版本、平台、架构、SHA-256、签名验证和 notarization 结果；
- 更新偏好使用独立的 `updates.json` schemaVersion 1 保存，避免升级核心 settings store 后阻止用户回退到 v0.4.0；
- 不实现自动二进制回滚。失败时保留当前可运行版本并给出手动下载入口；已安装新版本如需降级，只允许用户安装仍可验证签名的旧正式包，并明确提示数据兼容风险。

## 新依赖计划

阶段 4 计划增加运行时依赖 `electron-updater`。它与现有 electron-builder 的发布元数据和 NSIS/DMG 产物配合，统一 Windows/macOS 的检查、下载、进度和安装生命周期，避免分别维护两套平台更新协议。引入前必须锁定版本、审查传递依赖和默认网络行为，并用固定 provider 配置禁止 renderer 控制更新地址。

阶段 0–3 不增加该依赖；如果阶段 4 的验证发现其签名校验、代理行为或当前 Electron 版本兼容性不满足门禁，应暂停实现并回到本设计更新决策，不得以关闭签名验证作为回退。

## 发布信任链

正式发布按以下顺序完成：

1. 从干净且已标记的 Git 提交执行全部质量门禁；
2. 在目标平台构建对应架构产物；
3. 对应用、辅助进程和安装包执行平台签名；
4. macOS 产物提交 notarization 并完成 stapling；
5. 在隔离机器验证签名、安装、首次启动、升级和卸载；
6. 生成 SHA-256 与更新元数据，确认版本、架构和文件名精确匹配；
7. 最后发布 GitHub Release 和更新元数据。

任何签名、notarization、校验或上传步骤失败都必须中止发布。草稿 Release 不得被稳定客户端识别；重新构建同一版本必须使用新的预发布版本号，不能静默替换已经公开的产物。

## 更新状态与 IPC

shared 定义 renderer 可见的有限状态：`idle`、`checking`、`available`、`not-available`、`downloading`、`downloaded` 和 `error`。DTO 只包含公开版本、可选的脱敏发布摘要、下载百分比、是否允许安装和稳定错误码，不包含本地安装路径、请求头、令牌或原始 provider 响应。

具名操作包括：读取更新设置、修改自动检查开关、读取当前状态、手动检查、开始下载、取消尚未安装的下载和确认安装。订阅事件与快照采用“先订阅、后读取、按版本合并”的方式，避免窗口加载时序丢失状态。所有 IPC 请求通过 shared Zod schema 校验并使用现有 `registerIpcHandler` 注册。

## 安装安全与传输协调

更新服务查询传输队列、文件/文件夹协调器、配对流程和连接状态，只读取是否处于禁止重启的状态，不取得传输内容。下载完成后先显示版本和安装条件；用户点击安装时再次执行原子预检，避免确认后新任务刚好启动。

预检失败时保持已下载状态并说明原因，不取消任务、不强制断开连接。预检通过后先刷新恢复记录和 stores，再正常关闭服务与窗口并交给平台安装器。退出顺序复用现有安全关闭流程，不允许更新模块直接绕过传输清理、恢复持久化或退出确认。

## 隐私、日志与诊断

更新请求不附带 deviceId、公钥、设备名、局域网地址、历史、文件信息或恢复任务信息。日志只记录更新状态、公开版本、平台、架构和稳定错误码，不记录下载 URL 查询参数、认证头、凭据、安装路径或 provider 原始响应。诊断报告可以包含当前版本、更新设置和最后一次检查结果，但继续遵守同样的脱敏边界。

## 非目标

- 自动剪贴板同步、全局快捷键和开机启动；
- 二维码连接、多设备并发、群发和移动端；
- 公网中继、账号、云同步、遥测和崩溃上报；
- nightly、beta、灰度发布、强制升级和后台静默安装；
- 应用内任意下载器、插件更新或远程执行代码；
- 自动降级、跨大版本数据回滚和绕过平台信任提示。

## 分阶段路线

0. 本文档、产品边界、更新威胁模型、依赖理由、发布信任链和验收门禁；
1. shared 更新 DTO、状态、错误码、IPC schema、独立设置 store 与迁移/脱敏测试；
2. macOS Hardened Runtime、最小 entitlements、Developer ID 签名、notarization、stapling 和验证脚本；
3. Windows Authenticode 签名、NSIS 产物验证、发布者匹配和干净系统升级测试；
4. 引入 `electron-updater`，实现主进程固定来源检查、下载、状态机、频率限制和失败隔离；
5. Preload 具名 API、设置页更新偏好、手动检查、下载进度、发布摘要和错误体验；
6. 安装前原子门禁、活动传输协调、恢复记录刷新、安全退出和升级后启动确认；
7. 同一提交的可复现发布流水线、校验和、GitHub Release 草稿、凭据保护和发布审计记录；
8. v0.4.0 到 v0.5.0 升级/降级边界、安全攻击回归、Windows/macOS 实机矩阵和版本 `0.5.0` 候选发布。

每阶段独立执行 `pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm test` 和 `pnpm build`，存在测试脚本时不得跳过。阶段 2、3 和 7 需要用户提供对应平台证书、Apple 团队/notarization 配置及 GitHub 发布权限；缺少凭据时可以完成配置和无密钥测试，但不得伪造签名成功或正式发布结论。

## 当前实施状态

阶段 0 已完成范围、信任链、凭据边界和发布门禁规划。阶段 1 将实现 shared 更新契约与独立设置存储；当前尚未改变依赖、构建配置、应用版本或运行时行为。

- 更新源、稳定渠道、检查频率、用户控制和安装时机明确；
- 新依赖的用途、引入阶段和失败回退决策明确；
- IPC、renderer 沙箱、日志诊断和传输协调边界明确；
